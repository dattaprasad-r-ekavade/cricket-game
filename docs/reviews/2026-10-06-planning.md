# Planning review — 6 October 2026

Reviewed the repository at `3f90c38` after the first playable over and the gameplay regression pass in `docs/reviews/2026-10-06.md`. This is a plan and architecture assessment. It does not re-run `tools/review.ps1` or certify gameplay.

## Verdict

The plan is doing its job. Goal, assumptions, phases, gates, tool order, and AI rules are written down, and Steps 1–22 match the git history one commit at a time. Simulation stays graphics-free, assets are versioned JSON with validators, and `tools/review.ps1` is a real regression command.

The current product is a complete one-over prototype with a serious authoring and analysis pipeline. Cricket 07 presentation and a full match remain roadmap work.

## What the plan got right

- Scope stays Windows, offline, fictional teams, one stadium, over first, match later. Multiplayer and career stay deferred.
- `SuperCricket.Simulation` feeds the game, CLI analyzers, and the review script. Delivery, shot, field, and player assets validate before they run.
- Step notes record hashes, contact windows, the 10/2 sample over, and remaining limits.
- Metres, y-up, root motion, animation events, and clip names live at the Blender export boundary. Release timing is asset data.
- AI is a bounded coding, export, and analysis worker. Game simulation does not depend on an AI service.

## Findings

| Priority | Finding | Follow-up |
| --- | --- | --- |
| P1 | Starting assumptions were due for a rewrite after the first playable over. That over exists (Steps 6 and 22) and the rewrite was missing. | Record current assumptions in `plan.md`. |
| P1 | Delivery resolution (wide, no-ball, bowled, catch, boundary, run-out) lives as fields and methods on `Game1`. `OverScoreboard` only records a finished `DeliveryResult` for one over. | Extract a `DeliverySession` / match state into Simulation before innings. |
| P1 | Fielding uses a straight-line chase, 0.68 m radius, a presentation throw arc, a 1 m catch-height heuristic, and a 0.72 run-progress run-out cut. A longer match will copy those outcomes. | Add dedicated fielding and rules scenarios, then a match. |
| P2 | Phase 2 asked for timing and positioning. Wides produce zero contacts in the practice sweep because the batter does not step. | Footwork or leave before a fourth named shot. |
| P2 | Phase 0 still owes a batting/bowling/camera brief and a visual reference board. The code has a look; the intended look is not specified enough to judge Phase 4. | Write a one-page brief: feel, camera default, visual bar, hardware floor, keyboard versus controller. |
| P2 | The plan still describes in-game Delivery / Shot / Field labs. The CLI is already the source of truth for those jobs. | Keep the CLI; add F1 contact/release markers for live feel. |
| P2 | Assumptions list a controller. GamePad currently handles Back/Escape only. | Keep keyboard as the playable set until the short-match release maps a pad. |
| P3 | `Game1.cs` is about 1,300 lines and owns the match loop, input, batting, fielding presentation, scoring, cameras, HUD, capture, and review. | Split before Phase 5. |
| P3 | `SuperCricket.Game.csproj` copies `practice-attack.json` twice. Player JSON clips are about 7 MB in git. | Drop the duplicate copy; plan compressed or binary clips when more characters land. |
| P3 | There is no unit-test project. `DeliveryResult` and `OverScoreboard` are cheap to cover with xUnit as innings grow. | Add tests when match state moves into Simulation. |

## Recommended order of work

1. Keep the post-over assumptions in `plan.md` (this review).
2. Split `Game1` so delivery lifecycle and scoring resolution live in Simulation.
3. Grow fielding and rules scenarios (low catch, rope skim, throw while turning, no-ball catch with completed runs, crossed run on a four) from `--verify-gameplay` and `simulate-over`.
4. Add batter footwork or leave so the wide preset can be played.
5. Lock the short-match art bar as a readable stylized prototype, or plan a richer rig before chasing Cricket 07 fidelity.
6. Add live F1 markers for contact point, sweet-spot quality, and release/contact times.
7. Hygiene: duplicate field copy, clip size, and small scoring tests.

## Deferred on purpose

A second stadium, career mode, a spin catalogue, an MCP service over the CLI, and a general engine rewrite. The original plan already deferred those.
